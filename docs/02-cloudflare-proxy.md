# Зеркало для сетей, где блокируется Supabase

## Зачем это нужно

В рабочей сети провайдер блокирует `supabase.co`, поэтому основное приложение
`https://angelok199751.github.io/kanban_board/` не может достучаться до базы.
VPN включать не нужно: рядом публикуется **зеркало**, которое ходит в тот же
Supabase через бесплатный Cloudflare Worker.

```
обычное приложение:  браузер ──────────────────────────────► supabase.co
зеркало:             браузер ──► GitHub Pages /mirror/ ──► Worker ──► тот же supabase.co
```

Что это НЕ делает:

- не создаёт второй проект Supabase и не копирует данные;
- не меняет базу, RLS и пользователей;
- не меняет основное приложение: оно по-прежнему обращается к Supabase напрямую;
- не требует своего сервера, домена, банковской карты и ежемесячной оплаты.

Меняется только адрес базы в сборке зеркала. Все запросы — вход, таблицы,
RPC и WebSocket для совместного редактирования — идут через Worker.

## Что уже добавлено в репозиторий

| Файл | Назначение |
|---|---|
| `tools/proxy/cloudflare-worker.js` | Код Worker. Его нужно один раз вставить в Cloudflare |
| `tools/proxy/build-mirror.mjs` | Сборка зеркала в `dist/mirror` с адресом прокси |
| `.github/workflows/deploy.yml` | Шаг сборки зеркала, включается только при заданной переменной |
| `tools/test/ts/proxy.test.ts` | Проверки: чужой origin/путь не проксируются, CORS и WebSocket работают |

## Шаг 1. Создать Worker в Cloudflare (один раз)

1. Войди в Cloudflare → **Workers & Pages** → **Create application** →
   **Create Worker**. Выбери бесплатный план (Free), карта не нужна.
2. Название, например `qaflow-supabase-proxy`. Нажми **Deploy**.
3. Открой **Edit code**, удали шаблон и вставь целиком содержимое
   `tools/proxy/cloudflare-worker.js` из этого репозитория.
4. Нажми **Deploy**.
5. Скопируй адрес вида
   `https://qaflow-supabase-proxy.<твой-аккаунт>.workers.dev`.
   Это и есть прокси. Хвостовой слэш не добавляй.

Проверка: открой в браузере `https://<адрес-worker>/health`. Должен вернуться
JSON:

```json
{
  "ok": true,
  "service": "qaflow-supabase-proxy",
  "target": "https://kpwsonthpczijvcesgnj.supabase.co",
  "time": "..."
}
```

Если вместо этого ошибка Cloudflare — проверь, что код вставлен полностью и
нажат **Deploy**.

## Шаг 2. Разрешить адрес приложения

В `tools/proxy/cloudflare-worker.js` уже разрешены:

- `https://angelok199751.github.io` — GitHub Pages (и основное приложение, и зеркало);
- `http://localhost:<порт>` и `http://127.0.0.1:<порт>` — локальная разработка.

Если приложение когда-нибудь переедет на другой домен, поменяй константу
`GITHUB_ORIGIN` в коде Worker, снова нажми **Deploy** и пересобери зеркало.
Пока домен другой, Worker отвечает `403 Origin is not allowed` — это защита от
использования прокси чужими сайтами.

## Шаг 3. Задать адрес прокси в GitHub

1. Репозиторий → **Settings** → **Secrets and variables** → **Actions**.
2. Вкладка **Variables** → **New repository variable**.
3. Имя: `SUPABASE_PROXY_URL`.
4. Значение: `https://qaflow-supabase-proxy.<твой-аккаунт>.workers.dev`
   (без слэша в конце).
5. **Add variable**.

Это не секрет: адрес Worker всё равно виден в браузерной сборке. Секретный
ключ Supabase сюда класть нельзя — он и не нужен.

## Шаг 4. Пересобрать сайт

1. Вкладка **Actions** → **Deploy to GitHub Pages** → **Run workflow** →
   ветка `main` → **Run workflow**. Можно и просто отправить любой коммит в `main`.
2. Дождись зелёной галочки. Шаг **Build mirror (optional)** выполнится только
   потому, что переменная задана.
3. Зеркало откроется по адресу:

```
https://angelok199751.github.io/kanban_board/mirror/
```

4. Основное приложение останется на прежнем адресе и продолжит работать
   напрямую, без прокси.

Если переменную `SUPABASE_PROXY_URL` удалить или очистить, следующая публикация
соберёт только основное приложение. Зеркало останется от предыдущей сборки,
пока его не перезапишут; при желании старую папку `mirror` можно удалить
следующей публикацией без переменной.

## Что проверить с рабочего компьютера (без VPN)

1. `https://<адрес-worker>/health` открывается и показывает `"ok": true`.
2. Зеркало `/kanban_board/mirror/` открывается.
3. Вход своим логином и паролем проходит.
4. Доски и карточки загружаются, карточка создаётся и редактируется.
5. Перетаскивание карточки между столбцами сохраняется после обновления страницы.
6. Совместное редактирование: открой одну карточку в двух вкладках (или у двух
   людей), измени описание — второй видит правки и курсор.
7. То же для статьи в базе знаний.
8. Основное приложение `https://angelok199751.github.io/kanban_board/` без VPN
   по-прежнему открывается (может не соединиться с базой — это ожидаемо,
   для этого и сделано зеркало).

## Ограничения и безопасность

- **Бесплатный тариф Cloudflare Workers:** около 100 000 запросов в сутки и
  небольшой лимит CPU на запрос. Для четырёх человек этого с большим запасом.
  WebSocket-соединение считается одним запросом, сообщения внутри него
  отдельными запросами не тарифицируются. Лимиты видны в панели Cloudflare.
- **Данные не кешируются и не сохраняются** Worker'ом: он только передаёт
  запросы в Supabase. Логи Cloudflare могут хранить метаданные запросов
  (адрес, время, статус), как у любого сайта.
- **Worker не является заменой RLS.** Публичный ключ Supabase лежит в сборке
  и виден любому. Настоящая защита данных — правила RLS в базе; Worker лишь
  ограничивает, откуда браузер может к ним обращаться.
- **Разрешены только три группы путей:** `/auth/v1/*`, `/rest/v1/*`,
  `/realtime/v1/*`. Произвольные адреса, `storage` и чужие хосты отклоняются.
- **Целевой Supabase зашит в код.** Подменить его через URL запроса нельзя.
  Если проект Supabase когда-нибудь переедет, поменяй `DEFAULT_SUPABASE_URL`
  в Worker (или задай переменную окружения `SUPABASE_URL` в настройках Worker)
  и пересобери зеркало.
- **Вход на зеркале отдельный.** Адрес базы отличается, поэтому Supabase хранит
  сессию под другим ключом в `localStorage`. Один раз войти на зеркале нужно
  заново; на основном приложении сессия останется своей.

## Если что-то не работает

| Симптом | Что проверить |
|---|---|
| `403 Origin is not allowed` | Открыт другой домен. Добавь его в `GITHUB_ORIGIN` Worker и переопубликуй Worker |
| `404 Not found` | Запрос идёт не на `/auth`, `/rest` или `/realtime`; проверь адрес прокси в переменной |
| `health` работает, а вход нет | Переменная `SUPABASE_PROXY_URL` задана? Шаг сборки зеркала был зелёным? Перепубликуй сайт |
| `502 Supabase is unavailable...` | Cloudflare не смог достучаться до Supabase. Повтори через минуту; проверь статус Supabase |
| Ошибка CORS в консоли | Адрес Worker указан с путём или слэшем в конце; в переменной должен быть только `https://...workers.dev` |
| Realtime не синхронизирует | В DevTools → Network открой WS-соединение: должен быть статус `101`. Проверь, что Worker обновлён и WebSocket не блокируется сетью |
| Зеркало показывает старую версию | Обнови страницу с `Ctrl+F5`; проверь, что публикация прошла после изменения переменной |

## Как обновить или отключить прокси

- **Обновить код Worker:** открой Worker в Cloudflare → **Edit code** → вставь
  новую версию из репозитория → **Deploy**. Пересборка сайта не нужна, если
  адрес Worker не менялся.
- **Отключить зеркало:** удали переменную `SUPABASE_PROXY_URL` и опубликуй сайт
  заново. Основное приложение это не затронет. Worker можно удалить в Cloudflare
  или оставить — без адреса в сборке он не используется.
- **Откат:** в Git верни предыдущий коммит и отправь в `main`; GitHub Pages
  пересоберётся автоматически. Для срочного отключения достаточно удалить
  переменную и перезапустить публикацию.
