### 1.5 Выявленные проблемы и особенности
1. **Горизонтальная прокрутка:** `.board { overflow-x:auto }` не ограничен по высоте окна, поэтому растягивается вся страница; высота столбцов не ограничена. Нужен layout «шапка + панели + доска на `100dvh`».
2. **Нет удаления задач**, нет корзины.
3. **Архив смешан с активными** как обычный столбец.
4. **Порядок карточек не сохраняется**.
5. **Лимиты Apps Script:** ≈9 КБ на свойство, ≤30 представлений, ≤100 значений списка, ячейка ≤50 000 символов — в Supabase исчезают.
6. **Цвета** привязаны к строковому значению и листу; новые свойства получают цвета иначе, чем встроенные (это и есть «недоработка», которую вы описали) — будет единая модель.
7. **Код монолитный:** один файл на 5000 строк, всё в одном замыкании.
8. **Разное написание статусов** («ё»/«е») между листами — см. §4.2.
9. Тесты, документация, система версий отсутствуют.

## 3. Предлагаемая архитектура

### 3.1 Технологии
- **Фронтенд:** React + TypeScript + Vite. Причина: код нужно привести в порядок, а состояние здесь сложное (доски, представления, черновики, редакторы); React + типы даёт структуру. Сборка Vite даёт небольшой быстрый бандл; статичный сайт на GitHub Pages.
- **Drag-and-drop:** dnd-kit (столбцы и карточки, автопрокрутка у края, подсветка цели, ровные хэндлы, без случайного открытия карточки).
- **Данные:** `@supabase/supabase-js` (Auth + PostgREST + Realtime). Серверных функций не требуется.
- **Состояние:** TanStack Query (кэш, оптимистичные обновления с откатом при ошибке) + Realtime-подписка, которая обновляет кэш.
- **Текстовый редактор описаний:** небольшой контролируемый `contenteditable` как сейчас либо Tiptap; формат хранения тот же (HTML из белого списка). DOMPurify для очистки.
- **Структура репозитория:** `src/features/{board,editor,views,properties,knowledge,archive,trash,theme,auth}`, `src/lib/supabase`, `supabase/migrations/*.sql`, `tools/import/`, `docs/`.
- Тема/стили: переносим CSS-переменные текущего дизайна как есть, разбиваем на модули.

### 3.2 Хостинг и доступ
- GitHub Pages для приватных репозиториев доступна только на платных тарифах GitHub, а ограничение доступа по логину GitHub — только на Enterprise. Поэтому **репозиторий будет публичным**, и это безопасно, если выполнены три условия:
  1. В репозитории нет данных (xlsx, SQL с данными, `.env`, `service_role`) — `.gitignore` и проверка перед коммитом.
  2. Публичный ключ `sb_publishable_…` в коде — это нормально, он предназначен для браузера; защиту даёт **Row Level Security**, а не секретность ключа.
  3. Регистрация в Supabase закрыта, пользователи создаются вручную.
- Адрес будет вида `angelok199751.github.io/kanban_board/` (`base` в Vite, SPA без роутера по путям — hash-routing, чтобы не было 404 при обновлении).
- Деплой — GitHub Actions: сборка и публикация при пуше в `main`.

### 3.3 Вход по нику
Supabase Auth работает по e-mail. Решение без реальных почт: у каждого человека создаётся пользователь с технической почтой `<ник>@qaflow.local`, а форма входа просит **ник + пароль** и подставляет суффикс сама. Сайт принимает вход только так.
- Пользователи создаются вручную в панели Supabase (Authentication → Users), отключаются «Allow new users to sign up» и подтверждение почты.
- «Вшитый ник без пароля» небезопасен: в публичном сайте любой может открыть код и увидеть ник; пароль обязателен. Сброс пароля — через администратора (панель Supabase).
- `profiles` (ник, отображаемое имя) создаётся триггером.

### 3.4 Схема БД (черновик)

```
profiles(id uuid pk → auth.users, nickname unique, display_name, settings jsonb)

boards(id uuid pk, name, position, archived_at, next_number int default 1, created_at)
knowledge_bases(id uuid pk, name, position, archived_at, created_at)

board_properties(                         -- единый реестр свойств доски
  id uuid pk, board_id, key text,         -- key: 'исполнитель', 'тестовое', …
  title, type text check in ('text','url','select','date','longtext','title','number'),
  builtin bool, position int, hidden bool, legacy_header text)
property_options(                          -- значения списков + ЦВЕТ — для всех select-свойств
  id uuid pk, property_id, value text, color text, position int,
  unique(property_id, value))

board_columns(                             -- столбцы канбана, порядок отдельно от карточек
  id uuid pk, board_id, name, color, position int, is_hidden bool default false,
  unique(board_id, name))

tasks(
  id uuid pk, board_id, number int, title, column_id → board_columns,
  position text,                           -- дробный индекс (fractional indexing), порядок внутри столбца
  description text,                        -- HTML из белого списка
  props jsonb default '{}',                -- значения остальных свойств по property key
  archived_at, archived_by, deleted_at, deleted_by,
  version int default 1,                   -- оптимистичная блокировка
  legacy_id text unique,                   -- старый _id для идемпотентного импорта
  created_at, created_by, updated_at, updated_by,
  unique(board_id, number))

board_views(
  id uuid pk, board_id, owner_id nullable, -- NULL = общее стартовое представление
  name, position, config jsonb,            -- фильтры, сортировка, порядок/скрытие столбцов, поля карточки
  is_default bool)

knowledge_articles(id uuid pk, base_id, title, content, labels text, version int,
                   deleted_at, legacy_id unique, created_at, updated_at, updated_by)
```

Ключевые решения:
- **Порядок столбцов** — `board_columns.position` (общий для доски, как у вас сегодня в основном представлении). Порядок карточек — `tasks.position` (строка fractional indexing: вставка между двумя соседями меняет **одну** строку).
- **Статус = `column_id`.** Перемещение карточки меняет `column_id` и `position`; перемещение столбца меняет только `board_columns.position`.
- **Архив — отдельный признак `archived_at`**, а не статус. Задача в архиве не принадлежит активной доске, но сохраняет столбец-статус, из которого пришла. Мягкое удаление — `deleted_at` (корзина).
- **Цвета:** `property_options.color` для любого select-свойства; для статусов — `board_columns.color`. Новое свойство получает цвета тем же кодом, что и встроенные.
- **Представления:** общий стартовый («Все задачи») — `owner_id IS NULL`, одинаковый у всех; изменять его могут все (как сейчас, это основной вид), остальные — личные, видны только владельцу.
- Нумерация: `next_number` на доске + функция `create_task()` (атомарно, без дублей).
- Конфликты: `UPDATE … WHERE id=… AND version=…`; при несовпадении клиент показывает конфликт, как сейчас.

### 3.5 Безопасность (RLS)
- RLS включён на всех таблицах.
- Политики: все операции только `to authenticated` и только для пользователей из `profiles` (список из 4 человек). Анонимный доступ запрещён.
- Все пользователи видят общие доски/задачи/базы знаний и могут их менять; личные представления — только владелец (`owner_id = auth.uid() OR owner_id IS NULL`).
- «Окончательное удаление» из корзины и архива — через `SECURITY DEFINER`-функцию только для задач с `deleted_at`.
- Сам ключ — publishable; `service_role` нигде не используется.
- Проверка в приёмке: запросы с анонимным ключом без входа возвращают пусто/403.

### 3.6 Realtime
Подписка на `tasks`, `board_columns`, `board_properties`, `property_options`, `board_views`, `knowledge_articles`. События обновляют кэш; во время редактирования карточки входящее изменение того же поля показывается как конфликт, а не затирает ввод. Переставление карточек шлёт один запрос (одна строка).

### 3.7 Раскладка интерфейса (скролл)
```
100dvh
├─ шапка (фиксирована)
├─ панель представлений / фильтры / статистика (фиксированы)
└─ область доски: overflow-x:auto; overflow-y:hidden; flex:1; min-height:0
   └─ столбцы: ширина 280–320px, flex:0 0 auto
      └─ список карточек: overflow-y:auto (единственная вертикальная прокрутка)
```
Страница целиком не прокручивается. Отдельную полосу прокрутки внизу делаем **только если** встроенная окажется недоступной (длинная доска с вертикально обрезанным низом): по умолчанию доска занимает всё окно, и родная полоса уже у нижнего края. DnD автоскроллит по горизонтали у краёв.

### 3.8 Архив и корзина
- **Архив** — отдельный раздел в сайдбаре («Архив» под досками): таблица с поиском по номеру, названию, комментарию; просмотр карточки; «Вернуть на доску» (в исходный столбец), «Удалить» (в корзину). 
- Способы попасть в архив: кнопка «В архив» на карточке/в редакторе; массовое «Архивировать выбранные/все в столбце».
- Старый переключатель «Показать архив» убирается; вместо него раздел. Статус «Архив» из справочника при импорте не создаёт столбец (задач с ним сейчас нет); если встретится — такие задачи уходят в архив.
- **Корзина** — раздел: список удалённых, «Восстановить», «Удалить навсегда» (с подтверждением), автоочистка не включается.

## 4. Решения, которые принимаю по умолчанию (можно оспорить)

1. **Номера без значения:** задачам без номера присваиваются подряд числа от `max+1 = 43` в порядке строк листа; список выдаётся в отчёте импорта.
2. **Написание статусов:** берём из листа «143 релиз» (Ждем, Не берем) — это ваш рабочий лист. Список статусов в коде `STATUSES` («ё») не используется.
3. **Столбцы доски** = все статусы справочника, **кроме «Архив»** (он заменяется разделом). Пустые столбцы остаются, чтобы можно было перетащить карточку.
4. **Цвета:** начальные цвета статусов и значений задаются по палитре приложения; донастраиваются в интерфейсе.
5. **Настройки интерфейса:** тема, сайдбар, режим компактных карточек, развёрнутый редактор — остаются в `localStorage` (личное). Представления и порядок столбцов — в БД. Тему можно позже синхронизировать с профилем.
6. **Экспорт** — формирует данные из БД текущего представления.

## 5. Миграция данных

- Инструмент: `tools/import/build_seed.py` читает xlsx и создаёт **SQL-файл** (`INSERT … ON CONFLICT (legacy_id) DO UPDATE`), который вы запускаете в SQL Editor Supabase. Ключ `service_role` не нужен, в репозиторий файл **не попадает** (в нём ваши данные).
- Идемпотентность: `legacy_id` (старый `_id`) уникален; повторный запуск обновляет, а не дублирует.
- Отчёт: после вставки запрос выводит количество задач, статей, свойств, значений списков и сравнивает с исходными (36 / 1 / …). Скрипт также печатает список замечаний (задачи без номера, нераспознанные даты, пустые названия).
- Исходная таблица **не изменяется**; копию xlsx вы храните у себя как резервную.
- Резервное копирование и восстановление: `pg_dump`-инструкция + ежедневный экспорт из приложения (CSV/XLSX) + (платно) Point-in-time recovery Supabase.

## 7. Риски
- Я не могу подключиться к вашему проекту Supabase, а в моей текущей среде нет PostgreSQL и npm: миграции запускаете вы в SQL Editor, SQL-тесты и сборку приложения нужно прогнать отдельно (они пока не запускались). RLS и Realtime на вашем проекте проверим вместе после запуска.
